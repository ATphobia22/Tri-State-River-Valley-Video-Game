# Mount Vernon, Indiana — horizontal registration for game environments (v1.8)

## Purpose, sources and accurate limitations

The family video game uses official Indiana Geographic Information Office (IGIO) aerial imagery and already-digitized road/building vector geometry to improve the layout and art direction of the Mount Vernon, Indiana 47620 preview. This **is not a survey, routing application, regulatory map, high-confidence terrain reconstruction, or a 1:1 physical simulation**. Local browser saves are independent of real property information.

| Layer | Source | Reference vintage and confidence | Raw export |

| Overhead orthophoto | Indiana Current Imagery ImageServer (`di-ingov.img.arcgis.com`), public/CC0 | Identify operation at central Mount Vernon reports **2023**, 6-inch pixel size (other pixels of stitched image may vary by source tile) | `reference/mount-vernon/overhead.jpg` |

## Spatial reference / datum

The authoritative datasets above are requested as **EPSG:4326** longitude/latitude GeoJSON. The aerial ImageServer is queried using `bboxSR=4326,imageSR=4326`. Its returned bounds, **not merely the requested bounds**, control pixel-to-world registration, preventing offsets due to server-adjusted export aspect ratio.

The local game uses a deterministic horizontal affine approximation for artistic rendering:

```
longitude = -87.895000 + game_x * 0.00001137489
latitude  =  37.932500 - (game_z - 430) * 0.000009009399
```

This approximately represents metres near Mount Vernon but is **not a rigorous geodetic projection**; it has horizontal scale distortion with distance and does not establish a registered engineering CRS. Use an audited EPSG:2966 projection or local ENU transform for a future surveyed model, but do not silently reinterpret existing game units as US-survey-feet. The user's UE5 and tactical-engine reference documents use separate CRS/precision conventions that are **guidance**, not automatically an adopted game transform.

The 200×200 game terrain and rendered water level are **not** vertically surveyed. NAVD88 / GEOID18 corrections are not verified in this game. Only horizontal road/building/aerial registration can be compared with the source reference. Roof heights are **artistic approximations** (5–11 m), never copied from the authoritative polygon source (which lacks height data). Road elevation is sampled from the **same rendered game terrain**; it does not infer surveyed ground elevations from imagery.

## Reproducible acquisition, digitization and artwork

```bash
python -m pip install -r requirements.txt
python tools/acquire_mount_vernon_reference.py --out reference/mount-vernon
npm run build
npm test
python -m unittest discover -s tests -p 'test_reference_python.py' -v
```

The acquisition program paginates the official ArcGIS FeatureServer and asserts uniqueness and completeness of all `objectid`s, validates the image dimensions, and writes SHA-256 receipts. It overlays original GIS lines in yellow and building polygons in cyan onto the **unmodified official aerial** to produce `digitized-overview.png` for art reference. Exact source geometries remain preserved in `.geojson` without reduction; smaller quantized polygon rings / roads are generated only for low-LOD browser game performance. The offline HTML embeds both the actual reference raster and the rendered data for no-network gameplay.

`data/reference-bundle.js` is generated by the acquisition step and loaded by the game before `src/game.js`. The main scene and map consume the **same** source `roadsPacked` and `buildingsPacked`, with the aerial texture draped over the game's current terrain using returned pixel bounds. The new settings toggle `Show official overhead map and streets` controls a deliberately optional illustration overlay. The app remains playable if no reference bundle is installed or if the image decoder fails.

`registration.json` includes acquisition UTC, source URLs, source raster vintage identified downtown, returned bounds, dimensions, road/building counts, gameplay transforms, and datum warnings. `SHA256SUMS.json` plus the root `CHECKSUMS.sha256` provide independent file-integrity evidence.

## Quality gates and further engineering

- Required counts: 600+ official road segments and 4,000+ original building polygons within the documented bbox. A lower count stops the ingestion job; it must not silently substitute fictional data.
- Each official road and building is requested with WGS84 geometry, traced into game coordinates, and terrain draped. Reference maps use true projected pixel positions based on the returned aerial bounding box.
- Confirm horizontal registration with at least **three independent, verified surveyed control points** before claiming sub-metre or 1:1 accuracy. **Nearest-road anchor distances do not count** as such evidence.
- Reconcile roads, real building elevations, riverbank/river surface, photogrammetry, and terrain against orthorectified control/DEM before describing the world as seamless at survey scale. The current HLOD and 3D buildings are stylized.
- For future massive county/city areas, use spatial tiling, separate game and asset streaming layers, culling/hysteresis, mesh/texture LOD, asynchronous tile loads, and memory budgets per the user-provided internal docs; these do **not** imply UE5 World Partition already runs inside this Three.js browser game.
